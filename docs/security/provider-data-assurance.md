# Подтверждение условий обработки данных AI-провайдерами

## Границы гарантий

Правила организации проверяются сервером, а не браузером. Для чат-модели
требования no-training и ZDR должны одновременно подтверждаться действующей
версией каталога и операторским подтверждением конкретного подключения.
Отсутствие сведений, несовпадение подключения, истечение срока или несовместимая
настройка не считаются подтверждением. Повторная проверка выполняется перед
исполнением и отправкой попытки. Отключённые требования чата не вводят новых
ограничений доступа. Локальный mock не отправляет данные внешнему провайдеру.

ZDR относится к содержимому запроса у провайдера, а не к истории чатов,
документам, аудиту и учёту использования внутри SafeAI Desk. No-training
не означает ZDR. Настройка не меняет условия договора или режима API-аккаунта.
Платформа не может дистанционно удостоверить, как провайдер фактически
обрабатывает данные: оператор обязан проверить условия именно используемого
аккаунта, проекта, endpoint, модели и возможностей API.

Внешние embeddings и OCR требуют **обоих** подтверждений независимо от
политики чат-модели. Проверяются также фоновые операции индексации и OCR.
Внешние вызовы без действующего подтверждения блокируются. Локальные
hashing-embeddings и отключённый OCR не требуют внешнего подтверждения.
Для HTTP OCR доказательство должно охватывать все модели за endpoint:
смена не наблюдаемой клиентом внутренней конфигурации требует повторной
проверки оператором. Не предполагается автоматическое подтверждение всех
других внешних интеграций платформы.

## Настройка перед развёртыванием

1. Проверить актуальные договорные условия и фактический режим API-аккаунта.
   Хранить документы в защищённом реестре организации. Указать непрозрачный
   идентификатор записи с префиксом CONTRACT-, DPA-, DOC- или TICKET-; не
   включать имена, URL, токены, ключи и содержимое документов.
2. Установить время проверки и окончания действия в UTC ISO-8601.
   Максимальный период между ними — 90 суток, окончание исключительно.
3. Рассчитать отпечаток из точных эффективных параметров и действующего
   секрета. Примеры (пути и значения заменить на реальные):

```bash
python3 infra/scripts/provider-data-fingerprint.py openai-chat \
  --endpoint https://api.openai.com/v1 --model "$OPENAI_MODEL" \
  --store false --key-file /secure/path/OPENAI_API_KEY
python3 infra/scripts/provider-data-fingerprint.py anthropic-chat \
  --endpoint "$ANTHROPIC_BASE_URL" --model "$ANTHROPIC_MODEL" \
  --version "$ANTHROPIC_API_VERSION" --key-file /secure/path/ANTHROPIC_API_KEY
python3 infra/scripts/provider-data-fingerprint.py openai-embedding \
  --endpoint "$EMBEDDING_BASE_URL" --model "$EMBEDDING_MODEL" \
  --dimensions "$EMBEDDING_DIMENSIONS" --key-file /secure/path/EMBEDDING_API_KEY
python3 infra/scripts/provider-data-fingerprint.py http-ocr \
  --endpoint "$OCR_ENDPOINT" --key-file /secure/path/OCR_API_KEY
```

   Имена переменных в примерах — условные; использовать реальные параметры
   подключения, включая регистр и завершающий слеш URL. Можно передать
   `--key-env` с именем существующей переменной вместо `--key-file`.
   Утилита не печатает секрет, но отпечаток также не следует публиковать.
   OpenAI `store=true` несовместим с ZDR; `store=false` сам по себе
   ничего не подтверждает. Для внешнего подключения нужен HTTPS.
4. Добавить в доверенную конфигурацию deployment **только проверенные**
   значения. В Docker Compose используется env_file backend/.env.prod.
   Шаблон (не является реальным подтверждением, не копировать заполненным
   без проверки):

```dotenv
SAFEAI_PROVIDERDATAASSURANCE_CHAT_SOURCE=CONTRACT-REFERENCE
SAFEAI_PROVIDERDATAASSURANCE_CHAT_VERIFIEDAT=<UTC_ISO_8601>
SAFEAI_PROVIDERDATAASSURANCE_CHAT_EXPIRESAT=<UTC_ISO_8601>
SAFEAI_PROVIDERDATAASSURANCE_CHAT_CONNECTIONSHA256=<64_HEX>
SAFEAI_PROVIDERDATAASSURANCE_CHAT_NOTRAINING=true
SAFEAI_PROVIDERDATAASSURANCE_CHAT_ZERODATARETENTION=true
```

   Для embeddings и OCR создать отдельные блоки аналогичной структуры
   с EMBEDDING и OCR вместо CHAT и независимыми отпечатками.
   Не утверждать true для условий без подтверждения. Полностью отсутствующий
   блок означает «не подтверждено»; некорректный блок препятствует запуску.
   Эквивалентный префикс Spring: safeai.provider-data-assurance.chat,
   далее source, verified-at, expires-at, connection-sha256, no-training,
   zero-data-retention.
5. Обновить соответствующие сведения действующей версии каталога чата,
   перезапустить backend с новой deployment-конфигурацией, проверить
   диагностику и предварительную проверку правил. В production сначала
   проверить отсутствие потери необходимой функциональности в staging.
   Не отключать организационные требования для обхода отказа.

При ротации ключа, изменении endpoint, модели или других параметров привязки
старое подтверждение недействительно. Повторно проверить условия, обновить
отпечаток и срок. Для отзыва удалить соответствующий блок и перезапустить
сервис. Планировать пересмотр до истечения срока. Источник и сроки доступны
в диагностике и аудите решения, но не секрет и не отпечаток. Смена условий
у провайдера без изменения параметров требует немедленного ручного отзыва.

## Проверка релиза

Запустить `bash infra/scripts/test-provider-data-evidence.sh`,
`cd backend && ./mvnw -B -ntp clean verify` (включая обычные инфраструктурные
предпосылки проекта), в frontend — `npm ci`, `npm run typecheck`,
`npm run lint`, `npm run test`. Workflow Provider data assurance обязателен
для публикации production-образов; рекомендуется также сделать оба его job
обязательными проверками protected branch main. При красном CI не развёртывать.
Перед включением каждого внешнего канала проверить сценарий отказа без
подтверждения и успешное исполнение с утверждённым подтверждением в staging.

Миграция БД не требуется.

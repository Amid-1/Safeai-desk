# 7.5F.1 — Защита Redis и входного потока авторизации

## Границы

Первый подэтап RateLimit Production Hardening. Не меняет финансовые,
организационные, пользовательские и AI-лимиты, форматы существующих
HMAC-счётчиков, миграции V1–V101 или runtime ACL PostgreSQL.
Действующие ограничения обязательны независимо от новых барьеров.

### Nginx

| Вход | На IP | Burst | Весь edge | Burst |
| --- | ---: | ---: | ---: | ---: |
| Login | 5 req/s | 10 | 20 req/s | 40 |
| Refresh | 2 req/s | 10 | 100 req/s | 200 |

Превышение возвращает 429 до backend. Зоны используются совместно
воркерами одного Nginx, но не являются распределённым лимитером.
Обе размерности применяются одновременно. Источник IP — действующая
доверенная граница host Nginx; произвольный X-Real-IP клиента не доверяется.
Не связанные с авторизацией API и статические файлы не расходуют
auth-бюджет. Nginx не заменяет проверку в backend.

### Redis

До создания новой комбинации email/IP Lua проверяет обе размерности.
Если IP уже исчерпан, отсутствующий email-счётчик не создаётся.
Аналогично, исчерпанный email не создаёт новый IP-счётчик.
Существующие счётчики учитывают отвергнутые запросы; для отсутствующей
размерности не создаётся фиктивный счётчик, если запрос уже заблокирован.
Это не дополнительная возможность пройти аутентификацию: запрос не
выполняется вовсе. Первые N допущенных попыток и N+1-й отказ сохраняются.

Распределённая защита резервирует возможность аллокации до записи
счётчиков, markers, generations или одноразовых receipts.
На login допускается не более 4096 одновременно действующих резервов;
на refresh — не более 8192. Лимиты являются фиксированными защитными
потолками, не параметрами, которые можно случайно отключить.
Это **не** лимиты запросов к AI-провайдеру.

Login-резерв и запись выполняются в одном Lua-скрипте и одном
Redis Cluster slot. Резерв имеет срок, покрывающий самый длинный TTL
потенциально создаваемых ключей. Redis TIME определяет срок; истёкшие
резервы удаляются перед новой аллокацией. Повторные отказы при уже
существующем marker не расходуют новый бюджет аллокации.
Компенсация успешной аутентификации не возвращает резерв аллокации:
иначе можно создавать ключи по бесконечному числу новых email.

Refresh сохраняет существующую раскладку IP-счётчиков по Cluster slots.
Сначала резервируется один общий слот аллокации, затем атомарно
обновляется IP-счётчик. Резерв включает 10 секунд запаса между
вызовами; второе исполнение проверяет его абсолютный срок относительно
Redis TIME, не сокращая исходный TTL IP-счётчика. При просроченном
резерве или сетевой ошибке запрос закрывается. Для Cluster необходимы
синхронизированные часы серверов. Резервы не компенсируются даже после
неопределённого ответа Redis.

Структуры аллокации имеют постоянные имена, без email/IP, HMAC,
environment prefix или версии ключа. Защита от массового создания
ключей общая для инстансов приложения, использующих один Redis.
Нельзя совместно использовать этот Redis для независимых окружений,
если требуется независимая доступность их auth-бюджетов.

Верхняя граница для новых login-ключей — 7 на резерв (на практике
не все семь создаются одновременно). Для refresh — 1 IP-ключ на резерв.
После полного оборота старых окон это не более 28 672 + 8192
потенциальных активных ключей этих двух потоков, плюс две ограниченные
служебные ZSET. Это не ограничение на весь Redis: сессии, блокировки,
AI-лимиты и уже существующие ключи учитываются отдельно.

### Статусы и наблюдаемость

* 429 — превышение существующего лимита или исчерпание общего бюджета;
  серверный Redis-ответ сохраняет Retry-After. Для edge действует
  существующая семантика Nginx 429.
* 503 — ошибка Redis, OOM, повреждённая структура или истёкшая
  межслотовая refresh-авторизация. Fallback на PostgreSQL запрещён.
* Метрика rejected с dimension=capacity отличает общий барьер
  login/refresh от email/IP. Уведомления по существующим идентификаторам
  сохраняют исходный механизм deduplication; глобальный отказ не
  создаёт уникальных audit/marker ключей для произвольных email.
* Ни один из новых ключей/метрик не содержит исходный email или IP.

### Память

Production сохраняет maxmemory=192 MiB и noeviction; лимит контейнера
Redis повышен до 512 MiB (резерв 256 MiB) для RSS, AOF buffers,
репликационных буферов и copy-on-write. Local использует те же
ограничения. Это запас, а не доказательство достаточности памяти.
Перед deploy проверить суммарный ресурсный бюджет VPS и пики AOF rewrite.
При нехватке maxmemory Redis отказывает в записи, а не удаляет
ранее накопленные ограничения.

`infra/scripts/check-redis-memory.sh` читает только INFO/CONFIG,
не изменяет Redis; блокирует при noeviction mismatch, отсутствии
maxmemory, любом evicted_keys или 80% accounted memory/cgroup memory.
При невозможности чтения — ошибка, а не ложный PASS.
Периодические Prometheus/Grafana dashboards и Alertmanager — 7.5F.4
и Deployment Readiness.

## Развёртывание

1. Применить и проверить пакет на чистом Git-состоянии соответствующих
   файлов. Не перезаписывать собственные изменения.
2. Пересобрать backend и Nginx. Настройки в изменённом Nginx-файле
   сами по себе не обновляют уже запущенный образ.
3. Не смешивать old/new backend, пока старый код ещё может создавать
   ключи без общего барьера. В контролируемом окне остановить приём
   auth-трафика, заменить все экземпляры, затем снять блокировку.
4. Существующие Redis-данные не удалять; особенно не выполнять FLUSHDB,
   не менять namespace/HMAC, не пересоздавать production volume.
   Новая защита не ретроактивно резервирует старые ключи — сохранять
   noeviction и проверять память до выхода последнего старого окна.
5. Снять staging-метрики и запустить read-only memory probe.
   Ограниченная ёмкость — осознанный компромисс: распределённая атака
   может исчерпать общий auth-бюджет и вызвать временные 429
   легитимных запросов. Не отключать барьер; анализировать ingress,
   при необходимости пересматривать ёмкость и ресурсы как отдельный
   security-reviewed change.

## Приёмка

* 10 000 различных email с уже исчерпанного IP: ни одного нового ключа.
* 8192 распределённых login-попытки с разных email/IP, восемь потоков,
  два экземпляра limiter: ровно 4096 допущенных и bounded key count.
* Успешная компенсация, проводка generation/receipt, истечение окна,
  неисправный guard, общий budget при разных HMAC и namespace.
* Refresh: заполненный общий бюджет не создаёт новый IP-ключ.
  Существующий внешний Redis Cluster IT проверяет refresh на разных
  IP-ключах без CROSSSLOT (при предоставленном тестовом Cluster).
* Redis maxmemory/noeviction: отказ записи не удаляет старые счётчики.
* HTTP: isolated Nginx, distributed IP, per-IP refresh, подмена
  forwarded IP с недоверенного адреса, независимость остальных API.
* Полный Maven clean verify, mandatory report checks, Runtime ACL
  и производительность существующих модулей — без исключения тестов.

Не считать 7.5F.1 production accepted до реальных Redis/Testcontainers,
Nginx HTTP и полного backend-прогона. Отдельно остаются физические
RPM/TPM/конкурентность AI, HMAC-ротация самих счётчиков,
гарантии Redis Sentinel/restart, полноценные alerts и нагрузочная
приёмка мультиинстансного deployment.

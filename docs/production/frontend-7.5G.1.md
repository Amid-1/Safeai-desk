# SafeAI Desk — контракт frontend и backend (7.5G.1)

## Принцип

Backend — источник решений о доступе, лимитах, стоимости, состоянии AI-операции.
Frontend не отменяет их и не подменяет собственными догадками. Режим fail-closed,
CSRF, изоляция организаций, идемпотентность и миграции V1–V101 не изменены.

## Карта API и ответственности

- Auth — `/api/auth/login`, `/refresh`, `/logout`, `/me`, `/csrf`.
  Восстановление сессии не равно повторному входу; недоступность не означает неверный пароль.
- Users — `/api/users`: ADMIN в своей организации, SUPER_ADMIN в допустимой области API.
  Permanent deletion — SUPER_ADMIN, независимо от видимости кнопки.
- Organizations — `/api/organizations`: чтение своей карточки разрешено ADMIN;
  каталог, изменение, disable-impact, отключение и включение — SUPER_ADMIN.
- Chat — `/api/chats`: ADMIN/USER. POST `/{chatId}/messages` с clientRequestId;
  GET `/{chatId}/turns/by-client-request/{clientRequestId}` проверяет исходную операцию.
  Удаление с erasure — отдельное полномочие ADMIN, не обычный архив.
- Knowledge — `/api/knowledge-bases`: ADMIN/USER в пределах прав backend;
  индексирование, операция удаления и фактическая готовность не являются одним состоянием.
- Models — `/api/admin/models`: ADMIN/SUPER_ADMIN; изменение каталога и probe — только
  SUPER_ADMIN. Политика организации не изменяет физическое подключение модели.
- Usage — `/api/admin/usage`: ADMIN/SUPER_ADMIN. Общая сводка по организациям — SUPER_ADMIN.
  Подтверждённая стоимость, резерв и неизвестная стоимость не взаимозаменяемы.
- Audit — `/api/admin/audit-events`: ADMIN/SUPER_ADMIN; проверка integrity — SUPER_ADMIN.
  Независимая проверка журнала не фильтруется по текущей организации и периоду отчёта.
- RateLimit — 429 при превышении; 503 при недоступности механизма. Различать эти отказы.
- Observability — мониторинг, алерты и инфраструктурные параметры только для эксплуатации.

Восстановление Audit Outbox (`/api/admin/audit-events/outbox`), перестроение Usage
(`/api/admin/usage/rebuild`) и физическая AI-сверка — не повседневные действия пользователя.
Серверные проверки прав обязательны даже при прямом обращении к API.

## Публичные ошибки

- 400/422: исправить поля; только эти статусы отображают fieldErrors.
- 401: существующий протокол сессии и refresh; 403 не означает выход из аккаунта.
- 409: показать допустимое действие; конфликт версии не перезаписывать автоматически.
- 429: учитывать Retry-After (число секунд или HTTP-date), округлять вверх;
  при отсутствии корректного значения — локальная пауза 30 секунд, не гарантия допуска.
- 503: временная недоступность, а не неверные данные, не обход ограничителя.
- 5xx/сеть: безопасное описание и допустимый номер обращения для поддержки.
  Не отображать сырые серверные сообщения и fieldErrors 5xx в общем HTTP presenter.

## Состояния отправки чата

| Состояние UI | Разрешённое действие |
| --- | --- |
| SENDING | Дождаться ответа |
| PROCESSING | Проверить статус |
| SEND_UNKNOWN | Проверить статус, ручной повтор с прежним ID |
| RATE_LIMITED | Ручной повтор с прежним ID после паузы |
| RECONCILIATION_REQUIRED | Только проверить статус или скопировать текст |
| AMBIGUOUS | Проверить статус, скопировать или закрыть без повтора |
| FAILED / QUOTA_BLOCKED | Вернуть текст в черновик для осознанного нового запроса |
| ACCESS_REVOKED | Не отправлять повторно |
| IDEMPOTENCY_CONFLICT | Скопировать или закрыть без повтора |

При `AI_EXECUTION_RECONCILIATION_REQUIRED` неизвестный исход не становится разрешением
повторить POST после 404, ошибки GET или продолжающейся обработки. Чужой chatId либо
clientRequestId не применяется к текущему чату. Обработчик кнопки перепроверяет живое
состояние, первоначальный ID, блокировку отправки и активную сверку.

## Изоляция UI

Маршруты требуют подтверждённую аутентификацию и подходящую роль. При изменении
userId, organizationId или набора ролей защищённое дерево React монтируется заново.
Состояние старой страницы не переносится. Backend всё равно контролирует tenant scope.

## Приёмка

Обязательны typecheck, lint, Vitest, production build, проверки архитектуры и E2E.
На стенде проверить 401/403/409/429/503, отозванный доступ, смену tenant, повторный
POST и историю AI-запроса. Проверить негативные прямые запросы для всех трёх ролей.
Восстановление pending после перезагрузки вкладки требует отдельной проверки сценария
истории и серверной сверки; эта правка не добавляет хранилище текста в браузере.
Не считать этот этап выполненной общей production-приёмкой без зелёного CI и стенда.

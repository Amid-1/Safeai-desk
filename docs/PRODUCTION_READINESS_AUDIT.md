# SafeAI Desk — программа production-аудита

Срез: 20.11.2026, Stage 7.5A. Статус допуска: **NO GO до получения полного
набора доказательств**. Этот документ — программа проверки, не сертификат
безопасности и не отчёт о пройденных серверных испытаниях.

## 1. Этапы и границы

- 7.5A — инвентаризация, матрица контроля, исправление шторки журнала.
- 7.5B — реализация и негативные тесты серверных защит; устранение P0/P1.
- 7.5C — изолированный стенд: миграции, реальные инфраструктурные интеграции,
  восстановление, нагрузка, мониторинг, пробный выпуск и откат.
- 7.6 — независимая повторная проверка, подписанный отчёт и решение о выпуске.

Аудит начинается сейчас и продолжается при каждом изменении. Проверяются
все реально включённые функции, а не только страницы администратора.
Потенциальные возможности каталога не равны реализованным возможностям
адаптера. Нереализованные multi-provider/fallback, Tools, Vision, MCP,
OIDC/SCIM, DLP, расчёт по счёту провайдера и HA нельзя объявлять принятыми;
их наличие/отключение уточняется по актуальному checkout и конфигурации.

P0 — риск компрометации, изоляции, потери данных или обхода критических
ограничений; блокирует выпуск. P1 — существенный эксплуатационный риск;
блокирует выпуск, пока не устранён либо не принят владельцем с доказанной
компенсацией, сроком и ответственным. P2 — улучшение без критического риска.
Положительный тест недостаточен: нужны отказы, конкурентность и сбои.

## 3. Журнал событий: предметный аудит

В доступном срезе `AuditEventType` уже содержит семейства входа/выхода,
refresh reuse, rate limit, пользователей, организаций, чатов и erasure,
knowledge ACL/документов/ingestion/deletion/retrieval, AI response,
версий каталога/политик, решений маршрутизации и восстановления DLQ.
Наличие значения enum ещё не доказывает, что оно всегда записывается.
Для каждого события фиксировать вызовы emit, транзакционную границу,
источник actor и scope, тест и фактическую запись в стенде.

| Семейство | Дополнительные проверки покрытия |
| --- | --- |
| Авторизация | Отказ входа, отзыв сессии, reuse, изменение роли/статуса, попытки обхода; без записи секретов. |
| Администрирование | Кто, когда, какая организация и объект; изменение правила/каталога/гарантии, старая и новая версия, причина. |
| AI и бюджет | Решение allow/deny и reason code, отказ провайдера, soft/hard превышение, резерв/освобождение, корректная корреляция. |
| Knowledge и чаты | ACL, загрузка и скачивание, изменение, запрос и стадии удаления, hold и действия операторов. |
| Сам аудит | Просмотр чувствительных деталей и экспорт по утверждённой политике; retention, DLQ, изменение доступа, отказ и восстановление. |
| Инфраструктура | Успех/отказ деплоя, миграций, бэкапов, алертов, ротации секретов — в инфраструктурном журнале, не притворяться, что это события UI. |

Обязательные свойства записи: уникальный ID, серверное время UTC,
actor (или явный SYSTEM), затронутая организация, тип объекта и ID,
тип действия, итог и безопасный reason code, correlation/request ID,
связь версий где применимо. Snapshots имени/email нужны только при
обоснованной цели и допустимом сроке хранения. Не писать тело запроса,
пароль, ключ провайдера, cookie или содержимое чата/документа.

Для изменения критического состояния intent должен быть атомарен с
бизнес-транзакцией; повторная доставка — идемпотентна. Для отказов,
которые откатывают транзакцию, проверить независимый безопасный канал.
Не путать запрос на удаление с подтверждённым завершением. Прямой доступ
к БД привилегированной ролью — отдельная модель угроз: append-only
таблица сама по себе не защищает от администратора БД.

Интерфейс журнала: сохранить фильтры и pagination; улучшения по фактическому
инвентарю событий — категории (безопасность, управление, AI, знания),
уровень важности/результат, поиск correlation ID, быстрые пресеты отказов,
счётчики по серверным фильтрам, экспорт с указанием границ и урезания.
График нужен только для расследований; журнал остаётся первичным экраном.
Не заменять журнал красивыми, но недостоверными счётчиками.

## 4. P0: подтверждение preview правил

В доступном срезе `OrganizationModelPolicyController.createVersion`
вызывает сохранение напрямую; проверка UI не является серверным receipt.
Следующий этап требует сверки фактического DTO, сервисов, миграций и тестов.

Целевой контракт: сервер выдаёт короткоживущий одноразовый receipt после
симуляции. Связать его с actor, organizationId, ожидаемой версией,
каноническим хешем всех полей черновика (включая курс, лимиты и режим),
результатом проверки и подтверждением опасного изменения. При сохранении
повторно проверить права, актуальность версии, текущие критические
ограничения; атомарно потребить receipt и создать новую версию. Если
транзакция откатилась, состояние receipt должно быть согласованным.

Негативные тесты: нет receipt, истёк, подмена черновика, другая роль/actor/
организация, изменение каталога/гарантий, повторное и параллельное
использование, все модели закрыты без явного подтверждения, изменение
курса, stale version, откат транзакции. Preview не вызывает платного
провайдера и не расходует бюджет. Защиты runtime не ослабляются.

## 5. Матрица ролей и проверка по API

Для каждого endpoint и операции проверить анонимного, пользователя,
администратора своей организации, администратора чужой организации,
суперадминистратора, отключённого пользователя и отключённую организацию.
Ожидаемый доступ вывести из действующего контракта, включая ресурсные ACL.
Проверять HTTP/ответ, фактические изменения в БД, события и отсутствие
побочных вызовов. Тесты UI не заменяют прямые запросы к API.

## 6. Доказательства и решение о выпуске

Один каталог отчёта на SHA, например `audit-results/<git-sha>/` вне
публичного репозитория. Не публиковать секреты, PII и реальные запросы.

```text
audit-results/<git-sha>/
  00-scope.md             # SHA, окружение, границы, ответственные
  01-control-matrix.csv   # ID, статус, ссылка на доказательство
  02-findings.md          # Риски, воспроизведение, исправление
  03-ci/                  # Ссылки/санитизированные отчёты CI
  04-staging/             # API, browser, real infrastructure
  05-recovery/            # Backup/restore, RPO/RTO и сверка данных
  06-release/             # Digests, attestation, smoke, rollback
  07-decision.md          # GO/NO GO, подписанты, ограничения
```

Допустимые статусы: PASS, FAIL, NOT_RUN, N/A с доказанным обоснованием.
Для каждого контроля записать команду/сценарий, ожидание, фактический
результат, SHA, дату/часовой пояс, среду, артефакт, проверяющего. Для finding:
ID, severity, затронутый компонент, impact, воспроизведение, remediation,
ответственный, срок, повторный тест. Не хранить сырые секретные данные.

Шаблон строки:

| Контроль | Статус | SHA | Доказательство | Ответственный |
| --- | --- | --- | --- | --- |
| AI-02 | NOT_RUN | — | Нужен полный исходный код и тест | Backend |
| AUD-05 | NOT_RUN | — | Целевые тесты на срезе; E2E на реальном SHA ещё нужен | Frontend |

GO допустим при PASS всех P0, закрытых/официально компенсированных P1,
проверенном восстановлении, мониторинге, прохождении текущего CI, повторной
проверке исправлений и согласовании владельца выпуска. Отрицательный
результат или отсутствие обязательного доказательства — NO GO.

## 7. Исходные ограничения Stage 7.5A

Доступный снимок не является полным текущим checkout: отсутствуют части
конфигурации, тестов и инфраструктуры. Исторические CI workflow/README
показывают проектные меры, но не подтверждают текущий статус. Необходимы
полный санитизированный исходный код, свежие результаты CI, целевой профиль
развёртывания и разрешённый staging. Реальные API-ключи, .env, SSH-ключи,
дампы и production-логи передавать не нужно.

Архитектурные схемы и основной README сохраняются. После подтверждения
контролей обновить README актуальным статусом и ссылкой на этот документ.

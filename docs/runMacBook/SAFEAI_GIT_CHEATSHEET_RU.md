# SafeAI Desk — личная памятка: Git, Pull Request и сообщение коммита

Актуально на 25 октября 2026 года. Основная ветка `main` защищена правилом GitHub: изменения проходят через
Pull Request; проверки frontend и backend обязательны. Не делайте новые коммиты непосредственно в `main`.

**Разделяйте назначение файлов:** `commit-message.txt` в корне проекта содержит **только текст одного будущего
коммита**. Он исключён из Git через `.gitignore`. Команды, правила работы и запрос к ChatGPT храните в этой памятке,
а не в `commit-message.txt`. `git commit -F commit-message.txt` переносит в коммит всё содержимое файла буквально.

## 1. Начало новой задачи — создать рабочую ветку

Выполните из терминала macOS:

```bash
cd "$HOME/Workspace/Projects/Products/SafeAI-Desk"
git status -sb
git switch main
git pull --ff-only origin main
git switch -c feature/kratkoe-nazvanie-zadachi
```

Замените `feature/kratkoe-nazvanie-zadachi` на уникальное имя новой задачи, например
`fix/chat-message-validation`. Перед переключением желательно иметь чистую рабочую директорию; незакоммиченные
изменения не следует терять.

## 2. После правок — подготовить diff для проверки и сообщения

```bash
cd "$HOME/Workspace/Projects/Products/SafeAI-Desk"
git branch --show-current
git status -sb
git add -A
git restore --staged -- commit-message.txt
git --no-pager diff --cached --name-only
git --no-pager diff --cached --stat
git --no-pager diff --cached
git diff --cached --check
```

**Перед коммитом внимательно проверьте staged-файлы**, особенно после `git add -A`: не должны попадать пароли,
закрытые ключи, токены, `.env`, дампы с личными данными, локальные логи или случайные файлы. `.gitignore` не защищает
файлы, ранее добавленные в Git. Если появилось лишнее, снимите его с индекса командой
`git restore --staged -- <путь>` и проверьте diff повторно. Не отправляйте секреты в ChatGPT вместе с diff.

Если staged-изменений нет, создавать коммит не нужно.

## 3. Запрос к ChatGPT для подготовки commit-message.txt

Скопируйте запрос ниже вместе с выводом `git status -sb`, `git diff --cached --stat` и относящимся к задаче
`git diff --cached` (без секретов):

> Ты выступаешь техническим ревьюером изменений SafeAI Desk. Основная ветка `main` защищена, я работаю в отдельной
> Git-ветке и затем создаю Pull Request. По приложенному **staged diff** напиши готовое содержимое локального файла
> `commit-message.txt` для команды `git commit -F commit-message.txt`.
>
> Требования: русский язык и **прошедшее время**; первая строка — конкретный короткий заголовок коммита; после пустой
> строки — подробное, но точное описание реально сделанных изменений. Разделяй изменения функциональности, тестов,
> архитектуры, конфигурации и документации только если это следует из diff. Укажи проверки только тогда, когда я
> приложил их фактические результаты. Не приписывай этому коммиту предыдущие работы, уже объединённые в PR #17/#18,
> и не выдумывай изменённые файлы или исправленные ошибки. Не включай секреты. Если staged diff пустой либо данных
> недостаточно для конкретного утверждения, явно скажи об этом. В ответе дай **только текст сообщения коммита**,
> чтобы я мог сохранить его в `commit-message.txt`.

**Примечание:** ранее выполненные работы по PR #17 и #18 уже включены в `main`. Их ретроспективный текст можно хранить
как историческую заметку, но нельзя использовать в сообщении нового коммита, если эти изменения не входят в новый
staged diff.

## 4. Зафиксировать подготовленные изменения и опубликовать ветку

Вставьте подготовленное ChatGPT сообщение в корневой локальный `commit-message.txt`, убедитесь, что оно соответствует
staged diff, затем выполните:

```bash
cd "$HOME/Workspace/Projects/Products/SafeAI-Desk"
git branch --show-current
git status -sb
git diff --cached --check
git commit -F commit-message.txt
git --no-pager log -1 --stat
git push -u origin "$(git branch --show-current)"
```

Первый `git push -u` устанавливает upstream рабочей ветки; в следующие разы для неё достаточно `git push`.
Не выполняйте `git push origin main` для внесения изменений напрямую.

**Важно:** `git commit -m "..."` и `git commit -F commit-message.txt` — альтернативные способы задания текста коммита.
Если текст уже записан в файл, нужен `-F`, а не `-m`.

## 5. Pull Request и обязательные проверки

После push откройте ссылку на создание Pull Request, которую напечатал GitHub, либо перейдите в раздел
**Pull requests → New pull request** репозитория `Amid-1/Safeai-desk`.

В качестве базовой ветки выберите `main`, а в качестве сравниваемой — вашу `feature/...` или `fix/...` ветку.
Дайте PR название и описание **на русском**, проверьте вкладки **Files changed** и **Checks**. Дождитесь успешного
прохождения обеих обязательных задач:

- `Архитектура, ESLint, тесты и сборка` — frontend.
- `Java 21, Maven, архитектура и интеграционные тесты` — backend.

Только после успешных проверок и отсутствия нерешённых обсуждений используйте
**Merge pull request → Confirm merge**. Не обходите защиту ветки.

## 6. После успешного слияния PR — синхронизация Mac

```bash
cd "$HOME/Workspace/Projects/Products/SafeAI-Desk"
git fetch origin
git switch main
git pull --ff-only origin main
git status -sb
git --no-pager log -3 --oneline
```

Чистое состояние обычно отображается как `## main...origin/main`. Рабочую ветку можно удалить позднее после проверки,
что она больше не нужна.

### Замечания к отдельной памятке локального запуска macOS

- На опубликованной ветке `main` отсутствуют `scripts/start-local.sh` и `scripts/stop-local.sh`. Если они есть только
  на Mac, инструкции по ним относятся к локальным невключённым в Git скриптам; их работу без исходников подтвердить
  нельзя.
- Строка `4` в качестве адреса Vite неинформативна; обычно это `http://localhost:5173/`, но фактический адрес
  показывает `npm run dev`.
- В разделе ручного запуска backend не выполняйте `cd backend` повторно после перехода в корневую папку backend.
- Команду `./mvnw spring-boot:run` достаточно запускать один раз после экспорта переменных окружения.
- Для воспроизводимой установки frontend при наличии lock-файла в обычной ситуации предпочтительнее `npm ci`;
  проверка CI использует именно её.
- Настройки MinIO и пароль должны браться из локальных конфигураций, а не из непроверенных примеров. Не публикуйте
  настоящие `.env` и JWT-ключи.

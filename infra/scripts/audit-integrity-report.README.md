# Stage 7.5B.4.3 — независимая проверка и реагирование

## Граница доверия

`audit-integrity-report.py` выполняется на независимом verifier-хосте. Используется
только роль PostgreSQL `safeai_audit_verifier` с CONNECT, USAGE и SELECT на
`public.audit_events` из Stage 7.5B.4.2.1. IAM verifier разрешает чтение точных
версий S3, конфигурации и retention, но не PutObject/DeleteObject/изменение
retention. Не использовать runtime, migrator, DBA или ключи издателя архива.

Отчёт сравнивает текущий PostgreSQL-снимок с актуальным внешним закреплённым
контрольным снимком: вся цепочка, подписи, ротация, retention и отсутствие
неучтённого следующего bundle/permit проверяются до публикации. Счётчик
«Проверено закреплённых событий» — размер последнего внешнего снимка, включая
отсутствующие/подменённые записи. Новые записи отдельно учтены, не объявляются
криптографически подтверждёнными. Состояние PENDING не является нарушением само
по себе. Разрешённая, но ещё не завершённая операция retention блокирует зелёный
статус. Возвращение удалённой записи считается нарушением.

В backend поступает только подписанный файл статуса, без содержимого событий,
ключей архива, AWS/PG credentials или доступа к S3. Файл не заменяет доказательства
в WORM: при компрометации PostgreSQL выявляются различия с уже закреплённой
историей, но операции до первого закрепления не защищены от скрытой подмены.
Компрометация verifier, его ключа, внешнего pin или backend — другая модель угроз;
повтор свежего подписанного отчёта возможен в пределах 15 минут. Независимое
наблюдение за verifier и внешним хранилищем обязательно. Отчёт не является
основанием для автоматического удаления или повторной подписи истории.

## Подготовка на staging/production

1. Завершить приёмку Stage 7.5B.4.2.2 с реальным S3 COMPLIANCE. Хранить текущий
   pin вне PostgreSQL и приложения, обновлять его атомарно доверенным процессом
   из README архива. Настроить TLS PostgreSQL с `verify-full`, доверенным CA,
   `PGCONNECT_TIMEOUT=10`, учётными данными из защищённого хранилища. Настроить
   read-only IAM на verifier. Синхронизировать часы NTP.
2. Сгенерировать отдельный status-signing Ed25519 ключ только на verifier:

   ```sh
   umask 077
   openssl genpkey -algorithm ED25519 -out /secure/audit/status-private.pem
   openssl pkey -in /secure/audit/status-private.pem -pubout -outform DER | openssl base64 -A
   ```

   Последняя команда выдаёт публичный DER в Base64. Закрепить его и UUID
   dataset в доверенной конфигурации backend. Приватный ключ не копировать в
   Git, контейнер, `.env`, логи или на сервер приложения. При ротации этого
   отдельного ключа согласованно сменить pin публичного ключа и signer;
   старые отчёты перестанут проходить проверку. Это не ротация архивных ключей.
3. Запускать на verifier из доверенного checkout с защищённым окружением:

   ```sh
   python3 infra/scripts/audit-integrity-report.py \
     --dataset "$AUDIT_DATASET" --root-key-sha256 "$AUDIT_ROOT_SHA256" \
     --retention-key-sha256 "$AUDIT_RETENTION_SHA256" \
     --genesis-manifest-sha256 "$AUDIT_GENESIS_SHA256" \
     --bucket "$AUDIT_BUCKET" --account "$AUDIT_ACCOUNT" --retention-days 1095 \
     --pin /secure/audit/current-pin.json --status-private-key /secure/audit/status-private.pem \
     --output /secure/audit/out/status.txt
   ```

   Расписание каждые 5 минут, без параллельных запусков (systemd timer или
   эквивалент с взаимным исключением и ограничением времени). Планировать размер
   истории и длительность полного чтения цепочки; если не укладывается в SLA,
   не увеличивать TTL для маскировки проблемы. Коды выхода: 0 — VERIFIED,
   1 — UNAVAILABLE/отчёт не опубликован, 2 — VIOLATION, 3 — PENDING. Доставлять
   подписанный файл и при ненулевых кодах, если создан новый отчёт. Файл должен
   оставаться на стороне verifier; на сервер приложения передаётся только его
   подписанная копия по доверенному каналу, с атомарным rename в защищённом
   каталоге (владелец отдельного оператора, группа 10001, режим 0750 для каталога
   и 0640 для файла). Не разрешать backend писать туда. Не монтировать файл
   отдельно: при атомарной замене inode контейнер должен видеть новую версию.
4. Переменные окружения backend (только публичные данные):

   ```dotenv
   SAFEAI_AUDIT_INTEGRITY_REPORT_PATH=/run/audit-integrity/status.txt
   SAFEAI_AUDIT_INTEGRITY_DATASET=UUID_из_доверенного_конфига
   SAFEAI_AUDIT_INTEGRITY_PUBLIC_KEY=BASE64_DER_закрепленного_ключа
   ```

   Для Docker Compose на этапе 7.5C подключить read-only bind каталога в сервис
   backend через проверенную конфигурацию деплоя: `source` — защищённый каталог
   доставки на хосте; `target: /run/audit-integrity`, `read_only: true`,
   `bind.create_host_path: false`. Остальные ограничения и тома не менять.
   На локальном Mac можно задать путь абсолютным именем файла. Без этих трёх
   настроек карточка честно показывает «Независимая проверка не настроена».

## Реагирование и оповещения

Prometheus считывает gauge `safeai_audit_integrity_state` с каждой реплики.
Правила работают вместе с прежними правилами Audit Outbox и не заменяют их.

| Состояние | Условие | Реакция |
| --- | --- | --- |
| VERIFIED (1) | Подпись/архив/сравнение OK, новых незакреплённых событий нет | штатно |
| VIOLATION (2) | Подмена/удаление/возврат ранее удалённого события | critical, без задержки |
| UNAVAILABLE (3), STALE (4), INVALID (5) | Доверие или доступ не подтверждены | critical через 2 минуты |
| NOT_CONFIGURED (0) | Независимая проверка отсутствует | warning через 5 минут, NO-GO в production |
| PENDING (6) | Новые незакреплённые события | warning через 15 минут |
| Недоступная метрика | Нет heartbeat/метрики или scrape не успешен | critical через 3 минуты |

При нарушении: остановить публикацию новых checkpoint и retention, сохранить
сырой внешний pin, версии объектов, снимки и логи проверяющего; создать инцидент,
проверить независимую копию и расследовать источник. Не переподписывать историю
и не обновлять pin как способ закрытия инцидента. При недоступности — проверить
часы, IAM, TLS, роль reader, состояние подписи и доставки. Возобновлять только
после расследования с одобрением ответственного за безопасность.

В 7.5C подключить внешнюю маршрутизацию Alertmanager: critical — дежурный
безопасности с подтверждённой доставкой и эскалацией; warning — оператор.
Проверять доставку synthetic alert, сбой маршрута и восстановление, включая
отказ самого backend/Prometheus. Сейчас правила оцениваются в Prometheus;
email/Telegram/Slack не считаются подключёнными, пока не выполнена приёмка
реального маршрута. Не хранить webhook credentials в Git. До этих проверок,
настройки verifier и реального S3 — **NO-GO production**.

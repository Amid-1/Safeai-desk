# SafeAI-Desk: публикация, перенос БД и Production-допуск

Это основной эксплуатационный регламент релиза. Он не подтверждает, что
реальный backup уже восстановлен или что Production готов к переключению.

## Принципы безопасности

- **Publish и deploy разделены.** `.github/workflows/production-release.yml`
  собирает, сканирует, подписывает и публикует образы. Он не деплоит.
- `.github/workflows/production-deploy.yml` запускается отдельно, вручную,
  и использует digest образов из выбранного успешного `publish_run_id`.
- Нельзя подменять PostgreSQL-образ поверх существующего физического
  `safeai_postgres_data`. Нужен отдельный план логического переноса.
- Никогда не передавать рабочие дампы, ключи `age`, пароли и PGDATA в
  GitHub Actions, pull request, коммиты или чат.

## Этап 1. Проверить CI и подготовить резервную копию

До релиза убедиться, что все обязательные проверки текущего SHA успешны.
Получить проверенный `*.dump.age`, соответствующий файл `.sha256`, ключ
расшифровки и сведения об источнике. Зафиксировать согласованный snapshot
или окно без записи для инвентаризации строк.

Подробная процедура: [README-restore-rehearsal.md](README-restore-rehearsal.md).

## Этап 2. Опубликовать immutable-образы без деплоя

После review и слияния одобренных изменений в `main`:

1. Открыть GitHub → Actions → `Production release` → `Run workflow`.
2. Выбрать `main`. Workflow требует успешные проверки именно HEAD `main`.
3. Дождаться Trivy, CycloneDX SBOM, attestations и публикации в GHCR.
4. Записать **run ID** успешной публикации и скачать артефакт
   `safeai-published-images-<SHA>` с JSON-манифестом digest.

Повторный запуск публикации может получить другой digest. Для деплоя
выбирается **конкретный run ID**, а не пересобирается образ по тому же SHA.

## Этап 3. Восстановить backup на изолированном экземпляре

Проверить **точно опубликованный PostgreSQL digest** на новом пустом volume.
Не подключать исходный `safeai_postgres_data` и не публиковать сетевые порты.

Обязательные результаты:

- `pg_restore` без ошибок, проверка SHA-256 и версия PostgreSQL/pgvector;
- сравнение кодировки, локалей, collation provider и ICU параметров;
- индексы, ограничения, HNSW и реальные RAG-запросы;
- `Flyway validate` с исходниками того же приложения;
- сверка данных с согласованным snapshot источника;
- независимая сверка S3 WORM, tombstone, retention и legal hold;
- подтверждённое удаление временных контейнера и volume.

`rehearse-restore.sh` выполняет только часть этих проверок. Успешное
завершение скрипта само по себе **не означает Production-допуск**.

## Этап 4. Отдельно спланировать cutover рабочей БД

Подготовить и утвердить runbook: остановка записи, финальная копия,
новый volume, логическое восстановление, сверки, роли и credentials,
переключение приложения, мониторинг и план отката.

`infra/scripts/deploy-prod.sh` блокирует небезопасную замену PostgreSQL
при обнаружении существующего контейнера или неизвестного volume.
Не обходить эту защиту вручную ради запуска новой версии.

## Этап 5. Только после проверки разрешить deploy

После принятого restore/DBA/S3 review владелец защищённого GitHub
Environment `production` устанавливает переменную
`SAFEAI_NOBLE_RESTORE_APPROVED_IMAGE` в **точный digest PostgreSQL**.

После отдельного подтверждения завершённого переноса базы запустить
GitHub Actions → `Production deploy` на HEAD `main` и указать нужный
`publish_run_id`. Workflow сверяет манифест, SHA, attestations,
одобренный digest и параметры защищённого Environment.

**Не запускать Production deploy до фактических доказательств восстановления.**

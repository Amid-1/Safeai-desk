# SafeAI-Desk: отчёты о покрытии и безопасная репетиция Production restore

## Что теперь показывает GitHub

- **Java**: JaCoCo HTML и GitHub job summary с 12 модулями (покрытие строк, ветвей, разница с
  сохранённым baseline), а также число JUnit/Surefire кейсов и локальных IT.
- **Frontend**: встроенный Vitest V8 coverage HTML, GitHub summary и отдельный автономный
  `dashboard.html` с группами из `src/`.
- **Стиль**: ESLint и TypeScript по-прежнему обязательны; Python `check-java-style.py` проверяет
  Java-код на UTF-8 BOM, CRLF, табы, хвостовые пробелы и отсутствие LF в конце. Исторические
  нарушения закреплены в ревьюируемом baseline. Новые/увеличенные нарушения блокируют CI. Это **не**
  полный Google Java Format и **не** заменяет Qodana.
- **Тесты**: отдельные performance/Redis failover/Playwright тесты не подменяются процентом JaCoCo
  или Vitest. Их результаты смотрятся в соответствующих job. Графики показывают актуальный прогон и
  сравнение с baseline, **не** временной ряд прошлых релизов.

Открыть: GitHub → Actions → Проверка бэкенда / Проверка фронтенда → Summary. ZIP с `dashboard.html`
лежит в Artifacts соответствующего запуска; открой скачанный HTML локально в браузере.

## Репетиция восстановления именно реальной БД

**НИКОГДА** не передавать рабочий `PGDATA`, `safeai_postgres_data`, дамп или `age`-ключ в PR, логи,
GitHub Actions, чат или коммит. PR №19 пока не вливать в main и Production release не запускать до
этой проверки.

1. Получи **существующий зашифрованный** `*.dump.age` из настроенного backup-процесса и его
   `*.sha256` (источник: `infra/scripts/backup-postgres.sh`). Проверь, что бэкап относится к
   требуемому моменту и действительно читается. Файл и age identity хранятся локально или на
   отдельном доверенном сервере, вне репозитория.
2. После безопасной публикации образа без деплоя (`deploy_to_production=false` на `main`, когда PR
   разрешён к слиянию) возьми **именно** digest `ghcr.io/<owner>/safeai-postgres@sha256:<64hex>` из
   отчёта публикации. Не подставляй tag `latest`, `noble-amd64` или номер коммита вместо digest.
   Если образ ещё не опубликован, репетиция на **будущем Production digest не может быть
   проведена**. Можно провести предварительную на локально построенном образе в отдельном тестовом
   контуре, но результат не считается Production-допуском.
3. Проверь наличие Docker, `age` и Python 3 на доверенном тестовом Mac/Linux. При необходимости
   отдельно выполни `docker login ghcr.io` для приватного registry; скрипт не читает prod `.env`.
4. Запусти `bash infra/postgres/rehearse-restore.sh --image
   'ghcr.io/OWNER/safeai-postgres@sha256:DIGEST' --backup '/secure/...dump.age' --identity
   '/secure/age-identity.txt' --report-dir '/secure/new-restore-report'`. **Отчётный каталог должен
   быть новым.**
5. Скрипт сверит SHA256, загрузит pinned образ, создаст уникальный volume и container с `--network
   none` и **без опубликованных портов**, расшифрует backup напрямую потоком в `pg_restore
   --single-transaction`, проверит PostgreSQL 16, vector 0.8.7, индексную валидность, `collation` и
   Flyway history, а также снимет точные количества строк по таблицам. После исполнения удалит
   **только собственные временные** container и volume. На хосте останется отчёт; данные не
   сохраняются в plaintext-файле.
6. Для строгого сравнения с источником используй `infra/postgres/source-row-counts.sql`, но
   **результат должен быть снят из того же консистентного snapshot**, что и `pg_dump`, либо в
   согласованное окно остановленных записей. Если источник продолжал изменяться между выгрузкой и
   подсчётом, это не доказательство равенства. Отсортированный CSV/TSV передай в `--source-counts`.
7. Выполни на **изолированной восстановленной копии** дополнительный Flyway `validate` из того же
   приложения, проверки SQL/XML, HNSW, RAG, специфические бизнес-инварианты, сверку схемы и внешнего
   WORM-журнала удалений. Проверка только версий в `flyway_schema_history` **не** проверяет
   настоящие checksum Flyway.
8. Коллизии `collation` требуют анализа DBA. По документации PostgreSQL при изменениях необходимо
   пересоздать зависимые индексы (`REINDEX`), а затем обновить версию collation; `REFRESH VERSION`
   сам по себе не пересоздаёт индексы. Никаких автоматических `REINDEX` и `ALTER DATABASE` на
   действующем Production.
9. Только после всего этого владелец защищённого `production` Environment может установить
   `SAFEAI_NOBLE_RESTORE_APPROVED_IMAGE` равным **точному digest** опубликованного образа.
   `deploy-prod.sh` запускать исключительно после review. Сам скрипт репетиции не предоставляет
   никаких одобрений.

### Что остаётся непройденным без настоящего бэкапа

Репетиция с dummy-базой не заменяет: физическую совместимость старого PGDATA (его не монтируем),
точность реальных миграций Flyway, сравнение данных/индексов источника и цели,
приложение/RAG/WORM/retention, процедуры отката и реальную проверку секретов, IAM и сетевых
ограничений.

### Важное исправление восстановления

Ранее `infra/scripts/restore-postgres.sh` автоматически вызывал `docker compose up -d backend nginx`
из `EXIT trap`, в том числе при ошибке. Это небезопасно. Теперь требуется дополнительное явное
подтверждение, а backend и Nginx остаются остановленными после restore до отдельной проверки WORM и
допуска. Скрипт по-прежнему **разрушительный** при явном вызове на действующем контуре: не запускать
его для репетиции. Для тестов предназначен **только** `rehearse-restore.sh`.

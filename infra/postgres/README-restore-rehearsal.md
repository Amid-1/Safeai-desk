# SafeAI-Desk: изолированная проверка восстановления PostgreSQL

Этот регламент относится к переходу с Debian на Ubuntu Noble.
PostgreSQL 16, pgvector 0.8.7 и UID 999 сохранены, но совместимость
**реальной базы** должна быть подтверждена на отдельной копии.

## 1. Собрать входные данные

Нужны:

- реальный зашифрованный backup `*.dump.age` и соседний `*.sha256`;
- отдельный файл ключа `age` с ограниченными правами;
- точный digest опубликованного `ghcr.io/.../safeai-postgres@sha256:...`;
- настройки исходной БД и инвентарь числа строк;
- отчёты по S3 WORM, удалённым объектам, retention и legal hold.

Не сохранять дамп, ключи, секреты и персональные данные в Git, GitHub,
CI-артефактах или открытых каталогах. Использовать доверенный отдельный
Docker-хост. Для локальной репетиции до публикации можно собрать тестовый
образ, но **такой прогон не подтверждает будущий Production digest**.

## 2. Проверить источник

Только SELECT-запросы, без изменения работающей базы:

```bash
psql -X -At -F $'\t' -v ON_ERROR_STOP=1 \
  -f infra/postgres/source-db-settings.sql \
  > /secure/source-db-settings.tsv
```

SQL для подсчёта строк: `infra/postgres/source-row-counts.sql`.
**Сравнение возможно только для того же согласованного snapshot,**
что использовался для `pg_dump`, либо во время окна без записи.
Простой подсчёт после завершения выгрузки не доказывает равенство.

## 3. Проверить опубликованный digest в отдельном volume

Создать новый каталог отчёта. Передать только защищённые пути к файлам:

```bash
bash infra/postgres/rehearse-restore.sh \
  --image 'ghcr.io/OWNER/safeai-postgres@sha256:EXACT_DIGEST' \
  --backup '/secure/backup.dump.age' \
  --identity '/secure/age-identity.txt' \
  --source-db-settings '/secure/source-db-settings.tsv' \
  --source-counts '/secure/source-row-counts.tsv' \
  --report-dir '/secure/new-restore-report'
```

Скрипт использует `--network none`, новый временный Docker volume,
не публикует порты и не подключает Production env. Дамп передаётся
потоком из `age` в `pg_restore`. После проверки скрипт удаляет только
свои временные ресурсы. Открытый plaintext dump на хосте не создаётся.

Проверить `RESULT.txt`, `metadata-audit.txt`, сравнения источника и
`cleanup-status.txt`. При ошибке удаления контейнера или volume
нужно вручную исследовать оставшиеся чувствительные данные.

## 4. Проверить то, что скрипт не доказывает

- Выполнить настоящий **Flyway validate** из той же версии backend.
  Одинаковые номера миграций не подтверждают их контрольные суммы.
- Проверить HNSW и RAG на реальных выборках, FK, ограничения,
  индексы, бизнес-инварианты и согласованность производных данных.
- Сопоставить удалённые объекты и tombstone с независимым S3 WORM
  журналом, проверить версии, retention и legal hold.
- Проверить роли, credentials, резервные копии и возможность отката.

## 5. Особенности collation и индексов

При логическом восстановлении индексы создаются заново. Тем не менее
различия `LC_COLLATE`, `LC_CTYPE`, ICU, provider или семантики сортировки
требуют отдельного DBA review, в частности для уникальных индексов.

Для физического PGDATA изменение версии системной библиотеки локалей
может потребовать `REINDEX` зависимых индексов. Команда
`ALTER COLLATION ... REFRESH VERSION` **не перестраивает индексы**.
Не запускать `REINDEX` или `ALTER DATABASE` на работающем Production
без отдельного плана и резервной копии.

## 6. Результат и окончательный допуск

Сохранить время и происхождение backup, его SHA-256, точный image digest,
результаты сверок, выполненные команды и ответственного за review.
Проверка обязана завершиться отказом при отсутствии существенных
доказательств; тестовая пустая база не заменяет настоящий backup.

**Этот runbook не разрешает deploy автоматически.** После проверки
нужны отдельный план переноса и процедура из
[README-release-publish-deploy.md](README-release-publish-deploy.md).

Отчёты по тестам и покрытию описаны в
[README-quality-prod-drill.md](README-quality-prod-drill.md).

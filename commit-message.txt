feat: завершить enterprise MVP SafeAI Desk

Полностью доработан SafeAI Desk как production-oriented full-stack MVP корпоративного AI Gateway.
Проект приведен к более целостной enterprise-архитектуре: усилены RBAC, tenant isolation,
cookie-based security, refresh-session revocation, audit/usage контуры, user/organization management,
frontend admin UI и документация.

Основные изменения:

1. Backend security и аутентификация

- Усилена модель cookie-based authentication:
  - access token хранится в HttpOnly cookie;
  - refresh token хранится в HttpOnly cookie;
  - CSRF token выдается отдельной readable cookie;
  - frontend отправляет CSRF header для unsafe HTTP methods.
- Уточнена работа refresh-token rotation:
  - refresh tokens хранятся в БД только в виде hash;
  - при refresh старый token отзывается;
  - новый token создается в той же token family;
  - при reuse revoked refresh token отзывается вся token family.
- Усилена invalidation-модель через tokenVersion:
  - role change инвалидирует старые access tokens;
  - password reset инвалидирует старые access tokens;
  - user disable инвалидирует старые access tokens;
  - organization disable инвалидирует access tokens пользователей организации.
- Добавлена/актуализирована логика отзыва refresh-сессий:
  - при reset password;
  - при изменении ролей;
  - при отключении пользователя;
  - при отключении организации.
- UserStatusFilter проверяет актуальное состояние пользователя и организации:
  - пользователь включен;
  - организация включена;
  - organizationId в JWT совпадает с актуальной организацией пользователя;
  - tokenVersion в JWT совпадает с актуальным tokenVersion пользователя.
- Добавлена fail-safe инвалидация security-state cache через application events.

2. RBAC и user-management

- Уточнена ролевая модель:
  - SUPER_ADMIN имеет platform/global scope;
  - ADMIN имеет scope только своей организации;
  - USER имеет доступ только к своим чатам.
- Запрещено создавать пользователей в platform organization через обычный user-management endpoint.
- SUPER_ADMIN может создавать USER и ADMIN только в обычных customer organizations.
- ADMIN может создавать только USER внутри своей организации.
- ADMIN не может создавать ADMIN.
- ADMIN не может управлять другим ADMIN.
- SUPER_ADMIN не может быть создан или изменен через обычный user-management flow.
- Защищен platform admin:
  - нельзя отключить;
  - нельзя изменить роли;
  - нельзя сбросить пароль через обычный user-management;
  - нельзя редактировать через обычный user-management.
- Добавлена защита от self-destructive операций:
  - нельзя отключить самого себя;
  - нельзя менять собственные роли через user-management;
  - нельзя редактировать самого себя через user-management.
- Добавлено редактирование пользователя:
  - PATCH /api/users/{id};
  - можно изменить email и fullName;
  - при изменении email увеличивается tokenVersion;
  - при изменении email отзываются refresh-сессии пользователя;
  - публикуется событие инвалидации security-state cache;
  - операция пишется в audit как USER_UPDATED.
- Добавлен DTO UpdateUserRequest.
- Добавлен AuditEventType USER_UPDATED.
- Добавлена Flyway migration для USER_UPDATED audit event type.

3. Organization management

- Уточнена platform/customer organization модель:
  - SafeAI Platform используется только для platform-level admin;
  - обычные пользователи и администраторы создаются в customer organizations.
- SUPER_ADMIN управляет организациями:
  - создает организации;
  - переименовывает организации;
  - включает/отключает организации;
  - видит всех пользователей всех организаций.
- ADMIN видит только свою организацию.
- USER не имеет доступа к organization-management.
- Защищена SafeAI Platform organization:
  - нельзя переименовать;
  - нельзя отключить;
  - backend запрещает mutation даже при прямом API-запросе;
  - frontend скрывает опасные действия.
- При отключении организации:
  - отзываются refresh-сессии всех пользователей организации;
  - bulk increment tokenVersion для всех пользователей организации;
  - публикуется event инвалидации cache;
  - audit фиксирует requiresRelogin/sessionsRevoked.
- При повторном включении организации refresh tokens не восстанавливаются, пользователи должны войти заново.
- Добавлен endpoint получения текущей организации /api/organizations/me для ADMIN/SUPER_ADMIN.

4. Audit

- Audit events приведены к tenant-aware модели:
  - события содержат organizationId;
  - ADMIN видит audit только своей организации;
  - SUPER_ADMIN видит global audit и может фильтровать по organizationId.
- Добавлены и актуализированы audit events для:
  - user created;
  - user updated;
  - user enabled changed;
  - user roles changed;
  - user password reset;
  - organization created;
  - organization name changed;
  - organization enabled changed;
  - login success/failed/logout;
  - refresh token reuse;
  - chat events;
  - AI provider events;
  - rate limit exceeded.
- Усилен audit storage:
  - details приводится к non-null jsonb;
  - добавлен default '{}';
  - добавлены индексы для фильтрации по organization_id/event_type/created_at.
- Добавлена миграция V11 для USER_UPDATED в audit_event_types.
- Исправлена миграция V11: используется колонка name, так как audit_event_types имеет primary key name.

5. Usage analytics

- Уточнена usage-модель:
  - usage считается только по ASSISTANT messages;
  - учитываются только COMPLETED messages;
  - model должен быть не null.
- Добавлены/уточнены usage endpoints:
  - /api/admin/usage/summary;
  - /api/admin/usage/users;
  - /api/admin/usage/models;
  - /api/admin/usage/daily;
  - /api/admin/usage/by-user/{userId};
  - /api/admin/usage/by-organization/{organizationId}.
- Уточнены правила доступа:
  - SUPER_ADMIN видит global usage;
  - ADMIN видит usage только своей организации.
- Добавлены usage indexes для chat_messages:
  - global completed assistant usage;
  - organization completed assistant usage;
  - session completed assistant usage.
- Добавлены rollup tables для будущей оптимизации отчетов.
- Добавлены constraints на total_tokens = input_tokens + output_tokens.
- Зафиксированы правила date range:
  - dateFrom inclusive;
  - dateTo exclusive;
  - default range last 30 days;
  - maximum range 366 days;
  - daily usage grouped by UTC date.

6. Chat и AI provider flow

- Уточнен chat processing flow:
  - проверка ownership до обработки сообщения;
  - Redis lock защищает от параллельной отправки в один чат;
  - rate limit проверяется перед AI call;
  - USER message сохраняется отдельно;
  - внешний AI call выполняется вне длинной DB transaction;
  - ASSISTANT/FAILED message сохраняется после ответа provider.
- Добавлено отображение failed assistant messages на frontend.
- Уточнена AI provider abstraction:
  - Mock provider для local/demo;
  - OpenAI provider scaffold;
  - Anthropic provider scaffold;
  - retry/timeout/rate-limit/unavailable mapping;
  - pricing config для approximate usage cost.
- Cost estimation оставлен как approximate, не billing-grade.

7. Rate limiting

- Login rate limiting реализован через Redis:
  - лимит по email;
  - лимит по IP.
- AI message rate limiting реализован через Redis.
- Redis limiter использует атомарную fixed-window модель.
- Зафиксированы отложенные улучшения:
  - HMAC вместо SHA-256 для Redis keys;
  - email+IP combined limiter;
  - sliding window/token bucket;
  - более детальные лимиты по provider/model.

18. Production notes

- Уточнена HTTPS модель:
  - production cookies используют Secure=true;
  - публичная точка входа должна быть HTTPS;
  - TLS termination может быть на внешнем reverse proxy/load balancer/Cloudflare;
  - backend не должен быть доступен напрямую из Интернета.
- Уточнена модель Nginx/reverse proxy:
  - X-Forwarded-For;
  - X-Real-IP;
  - X-Forwarded-Proto=https.
- Prometheus endpoint должен быть доступен только из доверенной сети.
- Production secrets должны передаваться через environment variables или secret manager.
- Access JWT lifetime и access cookie lifetime должны быть синхронизированы.

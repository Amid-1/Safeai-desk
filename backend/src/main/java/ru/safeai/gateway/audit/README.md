## 1. Назначение

Audit отвечает на вопросы: кто, когда, что сделал, в отношении какой организации,
с каким результатом и какие безопасные метаданные позволяют расследовать операцию.

В модуле реализованы:

- обязательная транзакционная запись намерения аудита (Transactional Outbox);
- автономный обязательный и диагностический best-effort режимы;
- фоновые доставка, повторные попытки, backoff и dead-letter;
- проверка равенства доказательств при конфликте идентификаторов доставки;
- операторское восстановление с сохранением исходного ID и собственным аудитом;
- неизменяемые исторические снимки инициатора и целевой организации;
- ограничение доступа по ролям и целевой организации (tenant isolation);
- серверные категории, статистика, фильтрация, страничная и курсорная выдача;
- сквозная корреляция HTTP, AI, чатовых и фоновых операций;
- типизированные details, санитизация и ограничение размера данных;
- пакетная очистка по сроку хранения с межрепличной блокировкой;
- независимые SHA-256-снимки, Ed25519-подпись и цепочка контрольных снимков;
- внешний WORM-архив, протокол ротации ключей и разрешений на удаление;
- подписанный статус независимой проверки, API и панель для `SUPER_ADMIN`;
- мониторинг Outbox и криптографической проверки, правила оповещений.

Audit — журнал действий приложения, а не хранилище содержимого чатов, база
финансовых операций или SIEM. Он не заменяет платёжную reconciliation,
реестр физических AI-вызовов, резервное копирование и контроль доступа к данным.

### Границы ответственности

| Модуль | Ответственность |

| `audit` | Сохранение, доставка, чтение и контроль доказательств |
| `infra` | Независимый архив, проверяющий процесс и мониторинг |

## 2. Архитектура

### 2.1. Запись и чтение

```mermaid
flowchart TD
    A[Бизнес-операция] --> C[Фабрика команды аудита]
    C --> S[Санитизация и снимки]
    S --> W[AuditOutboxWriter]
    W --> O[(audit_outbox)]
    O --> P[AuditOutboxProcessor]
    P --> E[(audit_events)]
    P --> D[Dead-letter]
    D --> R[Восстановление оператором]
    R --> E
    E --> Q[Политика чтения и репозитории]
    Q --> H[REST API]
    H --> U[Журнал событий]
```

Контур записи и контур чтения разделены. Бизнес-модули передают событие через
`AuditEventService`, а не изменяют таблицу `audit_events` напрямую.

### 2.2. Независимый контур доверия

```mermaid
flowchart TD
    DB[(PostgreSQL)] -->|Только чтение| X[Проекция и хеширование]
    X --> S[Независимый подписант]
    S --> W[(Внешний WORM-архив)]
    S --> T[Независимый реестр pin]
    DB --> V[Verifier]
    W --> V
    T --> V
    V -->|Подписанный статус| F[Файл только для чтения]
    F --> B[Backend: проверка Ed25519]
    B --> U[Панель SUPER_ADMIN]
    B --> M[Prometheus]
    M -.-> A[Alertmanager: настройка стенда]
```

Приватные ключи подписи и доступ к WORM не передаются приложению. Backend получает
только ограниченные метаданные подписанного отчёта. Пунктир — эксплуатационная
интеграция, требующая отдельной настройки и приёмки.

## 4. Модель данных и PostgreSQL

### 4.1. Таблицы

| Таблица | Смысл |
| --- | --- |
| `audit_outbox` | Долговечное намерение аудита и состояние доставки |
| `audit_events` | Материализованные исторические доказательства |
| `audit_event_user_links` | Отдельная связь события с существующим пользователем (V70) |

`audit_outbox` и `audit_events` используют один UUID для одного доставляемого
события. Это логическое соответствие, а не внешний ключ между таблицами.
После успешной доставки строка Outbox удаляется.

### 4.2. Поля доказательства

Все 11 полей `audit_events`, включая nullable значения, входят в контрольный снимок V94.

| Поле | Назначение |
| --- | --- |
| `id` | UUID события, ключ идемпотентной доставки |
| `actor_user_id` | Исторический идентификатор инициатора, может отсутствовать |
| `actor_organization_id` | Организация инициатора на момент события |
| `actor_email` | Исторический email инициатора |
| `actor_display_name` | Историческое отображаемое имя |
| `organization_id` | Целевая организация события, граница tenant scope |
| `target_organization_name` | Историческое название целевой организации |
| `event_type` | Код из `AuditEventType` |
| `details` | Ограниченный JSONB с безопасными метаданными |
| `created_at` | Время произошедшего события |
| `correlation_id` | Диагностический UUID операции, nullable для истории |

В Outbox дополнительно хранятся `occurred_at`, `created_at`, `attempt_count`,
`next_attempt_at`, `last_error`, `dead_lettered_at`.
При доставке `occurred_at` становится `audit_events.created_at`.

Инициатор и целевая организация — разные сущности. Например, супер-администратор
изменяет AI-политику Demo Company: actor относится к платформе, target — к Demo Company.
История не должна измениться при переименовании организации или удалении пользователя.
Таблица живых связей содержит только технические FK-ссылки на событие и пользователя.
Удаление любой стороны каскадно удаляет ссылку, а не историческое доказательство.

### 4.3. Миграции и ACL

| Миграция | Назначение |
| --- | --- |
| V5, V9–V11, V15 | События, индексы, ограничения и раннее расширение журнала |
| V18, V19 | Снимки инициатора и события управления пользователями |
| V24, V26, V27 | Outbox, повторная доставка, индексы и очистка |
| V37 | Снимки целевой организации |
| V68 | Защита неизменяемых полей, состояний Outbox и терминальных записей |
| V69, V70 | Отделение живых FK-связей от исторического доказательства |
| V75 | Событие операторского восстановления dead-letter |
| V79, V83, V84 | События удаления и контроля хранения знаний |
| V94 | Correlation ID, частичные индексы и иммутабельность новых полей |

Это основные профильные миграции, а не полный перечень изменений соседних модулей.
V93 относится к подтверждениям preview AI-политик; она не вводит таблицу аудита.
Этапы 7.5B.4.1–7.5B.4.3 не требуют новых миграций.

- `AuditEventEntity` использует ORM `@Immutable`; DB-триггеры запрещают подмену истории.
- Runtime ACL предоставляет только необходимые права, не владение схемой.
- `audit_events`: чтение, вставка, удаление по предусмотренным операциям; UPDATE не разрешён.
- `audit_outbox`: UPDATE только в рамках допустимых переходов, контролируемых БД.
- Внешний `safeai_audit_verifier` — отдельная роль, не runtime и не migrator.
- Flyway runtime ACL review фиксирует границу V94 и проверяет SHA-256 миграций.

Ограничения runtime не защищают от всех действий владельца схемы или DBA.
Для независимого обнаружения подмены используется отдельный криптографический контур.

## 5. Запись и доставка

### 5.1. Три режима записи

| Режим | Транзакция | Гарантия |
| --- | --- | --- |
| Обязательный в текущей транзакции | `MANDATORY` | Изменение и Outbox коммитятся вместе |
| Обязательный автономный | `REQUIRES_NEW` | Ошибка записи возвращается вызывающему коду |
| Диагностический best effort | Отдельная транзакция | Сбой не отменяет исходный результат |

Для важных изменений требуется обязательный режим. Успешный commit означает
сохранённое намерение аудита, но не мгновенное появление строки в журнале.
Если сохранение намерения не удалось, бизнес-транзакция должна быть отменена.

Типизированные вызовы используют `AuditDetails` и `createTyped`.
Не следует заменять required audit на best effort ради успешного ответа API.

### 5.2. Асинхронная доставка

```mermaid
sequenceDiagram
    participant S as Бизнес-сервис
    participant O as PostgreSQL Outbox
    participant W as Обработчик
    participant E as PostgreSQL Audit
    S->>O: Изменение + намерение в одной транзакции
    O-->>S: Commit
    W->>O: Выбор готовой строки с SKIP LOCKED
    W->>E: INSERT с прежним UUID
    alt Новая строка или доказательства совпадают
        W->>O: DELETE в той же транзакции
        Note over W,E: Commit доставки
    else Сбой или конфликт доказательств
        Note over W,E: Rollback доставки
        W->>O: Зафиксировать ошибку и следующий retry
    end
```

Обработчик выбирает готовые записи через `FOR UPDATE SKIP LOCKED`. Несколько
реплик могут обрабатывать разные строки без общей JVM-блокировки.
Каждое событие доставляется в отдельной транзакции `REQUIRES_NEW`.

Обычный INSERT использует `ON CONFLICT (id) DO NOTHING`. При конфликте
`AuditDeliveryEvidence` требует точного совпадения всех immutable полей истории
и Outbox, включая JSONB, исходное время и Correlation ID. Сравнение nullable
значений осуществляется через `IS NOT DISTINCT FROM`.

Если содержимое отличается, выбрасывается `AuditEvidenceConflictException`,
строки сохраняются для расследования и фиксируется метрика конфликта.
Прежнее поведение «одинаковый UUID достаточно» усилено в 7.5B.4.1.

### 5.3. Повторы и dead-letter

```mermaid
flowchart TD
    P[Готовая запись] --> A{Доставка успешна?}
    A -->|Да| E[История сохранена]
    A -->|Нет| N{Лимит попыток?}
    N -->|Нет| B[Отложенный повтор]
    B --> P
    N -->|Да| D[Dead-letter]
    D --> R[Решение SUPER_ADMIN]
    R -->|Совпадение доказательств| E
    R -->|Ошибка или конфликт| D
```

По умолчанию начальная задержка повтора — 2 секунды, максимальная — 1 час,
лимит попыток — 10. Retry и время хранения опираются на часы PostgreSQL.
Dead-letter не исчезает по исчерпанию повторов. Терминальное состояние нельзя
сбросить произвольным UPDATE. `last_error` не содержит сырого сообщения исключения.

### 5.4. Восстановление оператором

`POST /api/admin/audit-events/outbox/dead-letters/{eventId}/recover`.

Только `SUPER_ADMIN`. В одной транзакции сервис:

1. Блокирует исходную строку и проверяет терминальное состояние.
2. Материализует событие под исходным UUID или проверяет равенство доказательств.
3. Записывает обязательное событие `AUDIT_OUTBOX_DEAD_LETTER_RECOVERED`.
4. Удаляет восстановленную строку Outbox и коммитит изменения.

Результат: HTTP 204; отсутствующий ID — 404; pending или конфликт evidence — 409.
Любой сбой обязательной записи восстановления откатывает всю транзакцию.
Не исправлять конфликты ручной перезаписью события или обнулением счётчика retry.

## 6. Классификация событий

`AuditEventType` — источник машинных кодов. `AuditEventClassification` определяет
серверные категории и показатели. Классификация не изменяет историческую запись.

| Категория | События и смысл |
| --- | --- |
| `SECURITY` | Вход, выход, rate limit, обнаружение повторного refresh token |
| `USERS` | Создание, изменение, роли, блокировка, пароль, окончательное удаление |
| `ORGANIZATIONS` | Создание, переименование, изменение активности организации |
| `AI` | Чаты, сообщения, AI-ответы, каталог, политика, маршрут, удаление чатов |
| `KNOWLEDGE` | Базы знаний, участники, документы, ingestion, retrieval, erasure |
| `SYSTEM` | Операторское восстановление dead-letter |

В частности, `MODEL_POLICY_VERSION_CREATED` показывает изменение правил AI,
`MODEL_ROUTE_DECIDED` — разрешённое решение маршрутизации,
`MODEL_ROUTE_DENIED` — отказ. Preview и токен подтверждения политики относятся
к модулю `model`, а не к реализации криптографического архива аудита.

Сводка `AuditEventSummary` содержит `total`, `successful`, `denied`, `critical`.
Она считается на сервере по доступной выборке до пагинации.
При вычислении карточек активный фильтр `metric` исключается, остальные сохраняются.
Обе границы периода обязательны для сводки; запрос ограничен таймаутом 10 секунд.

| Показатель | Семантика |
| --- | --- |
| `total` | Все события, удовлетворяющие базовым фильтрам |
| `SUCCESS` | Явно классифицированные успешные исходы |
| `DENIED` | Ошибка входа, отказ AI-маршрута, превышение rate limit |
| `CRITICAL` | В текущей классификации `SECURITY_REFRESH_REUSE_DETECTED` |

`SUCCESS`, `DENIED` и `CRITICAL` — не исчерпывающее разбиение журнала.
Нейтральные события и ошибки выполнения могут не входить в эти показатели.
Критичность по смыслу независима от результата операции.
Криптографическое нарушение отражается в отдельной панели и метрике, а не
автоматически в счётчике `critical` прикладных событий.

### 7.2. Tenant isolation

```mermaid
flowchart TD
    A[Запрос API] --> R{Роль}
    R -->|ADMIN| T[Принудительно своя организация]
    R -->|SUPER_ADMIN| G[Глобальная область или фильтр]
```

### 7.3. Фильтры

| Параметр | Семантика |
| --- | --- |
| `eventType` | Код события |
| `userEmail` | Нормализованный email или префикс, до 320 символов |
| `userId` | UUID исторического инициатора |

Интервал `[dateFrom, dateTo)` допускает обе календарные даты UI посредством

границы, backend допускает до 367 суток с учётом DST; UI — до 366 календарных дней.

### 7.4. Пагинация

- Страничная выдача: размер по умолчанию 50, максимум 100, OFFSET до 10 000.
- Курсор: `limit` от 1 до 100, по умолчанию 50; размер токена до 512 символов.
- Порядок по умолчанию и для курсора: `created_at DESC, id DESC`.
- Для страничной выдачи разрешены `createdAt`, `eventType`, `organizationId`, `id`;
  если сортировка не содержит `id`, он добавляется как последний критерий.
- Токен v1 содержит timestamp и UUID в URL-safe Base64.
- Курсор не подписан и не связан с отпечатком фильтра: передавать прежние фильтры.
  Он не является полномочием; tenant scope всегда пересчитывается сервером.
- Keyset-пагинация не обещает MVCC-снимок всей истории на протяжении всех запросов.

Стабильный DTO страничного ответа: `content`, `number`, `size`, `totalElements`,
`totalPages`. Курсорный ответ: `items`, `nextCursor`, `hasNext`.
В `AuditEventResponse` поля `userId`, `userEmail` совместимы со старыми клиентами:
они содержат исторический снимок инициатора, а не данные текущего пользователя.

## 8. Сквозной Correlation ID

Этап 7.5B.3 связывает события одной операции для расследования и поиска в логах.
Корреляция принадлежит серверному контексту, а не произвольному идентификатору клиента.
`RequestIdFilter` создаёт серверный UUID, возвращает его в HTTP `X-Request-Id`
и помещает в MDC (`requestId`). Входящий `X-Request-Id` обрабатывается отдельно
как недоверенный `clientRequestId` и не используется для серверной корреляции.

V94 добавляет nullable UUID в пять таблиц:

- `audit_events`;
- `audit_outbox`;
- `model_route_decisions`;
- `chat_turns`;
- `knowledge_ingestion_jobs`.

```mermaid
flowchart TD
    R[Контекст операции] --> C[CorrelationContext]
    C --> A[Audit intent]
    C --> M[Решение модели]
    C --> T[Chat turn]
    C --> K[Ingestion job]
    A --> E[История аудита]
    T --> F[Фоновое восстановление]
    K --> F
    F --> E
```

`AuditCommandFactory` берёт текущий ID или создаёт новый при отсутствии контекста.
Фоновые обработчики восстанавливают сохранённый контекст на время операции
и закрывают его после выхода, не допуская утечки между задачами.

ID переносится из Outbox в историю, участвует в сравнении evidence и внешнем хеше.
Исторические строки остаются `NULL`: миграция не выдумывает связи задним числом.
V94 защищает новые поля от изменения и добавляет частичные индексы в нужных таблицах.
Correlation ID не заменяет авторизацию, ключ идемпотентности, audit event ID
или криптографическую подпись. Он не меняет существующий decision hash модели.

В интерфейсе доступны дополнительный фильтр UUID, копирование Correlation ID
и переход «Найти связанные события» из подробностей события. Значение включено в CSV.

## 9. Защита метаданных

Типизированные `AuditDetails` проходят `AuditCommandFactory.createTyped` и
`AuditDetailsSanitizer`. Нетипизированный `Map` проверяется по отдельному allowlist
текстовых ключей. Типизированный объект не даёт разрешения записывать произвольный текст.

Санитайзер контролирует Unicode, нормализацию NFKC, глубину, число узлов, длины строк,
размер чисел, допустимые типы и итоговый JSON. Распознанные секреты редактируются.
При превышении бюджета используются явные маркеры, например `[REDACTED]`,
`[MAX_DEPTH]`, `[BUDGET_EXCEEDED]`, `[OMITTED_UNAPPROVED_TEXT]`.

| Источник | Допустимое доказательство |
| --- | --- |
| Auth refresh reuse | ID семейства, допустимый IP, SHA-256 User-Agent |
| Login rate limit | HMAC-отпечатки email/IP, системный инициатор |
| AI/Chat | Тип результата, ID и разрешённые диагностические поля |
| User/Organization | Исторические снимки, факт изменения |
| Восстановление очереди | Исходный UUID и число попыток |

Запрещено сохранять prompt, ответ модели, raw User-Agent, пароли, access/refresh token,
ключи API, DB credentials, приватные ключи, HTTP bodies и сырые тексты исключений.
Снимки email и IP могут содержать персональные данные; применять privacy policy,
ограниченный доступ и согласованные сроки хранения. Санитайзер не гарантирует
распознавание абсолютно всех секретов — ответственность лежит и на вызывающем коде.

## 10. Криптографическая целостность

### 10.1. Контрольные снимки (7.5B.4.2.1)

Контрольный снимок (checkpoint) — подписанный манифест идентификаторов и SHA-256
неизменяемых полей `audit_events`. Он не содержит текстов событий.

```mermaid
flowchart TD
    A[Согласованный снимок PostgreSQL] --> B[Каноническое представление 11 полей]
    B --> C[SHA-256 каждой записи]
    C --> D[Манифест UUID и хешей]
    D --> E[Ed25519-подпись]
    E --> F[Внешнее хранение и pin]
```

`audit-checkpoint-export.sql` формирует согласованную проекцию PostgreSQL V94.
`audit-checkpoint.py` поддерживает capture, sign и verify. Подписанный снимок
содержит dataset UUID и SHA-256 предшественника. При сравнении выявляются изменения
и исчезновение закреплённых записей, а новые записи учитываются отдельно.
Исходные строки обрабатываются доверенным процессом по TLS; не сохранять их на диск
и не логировать. Формат зависит от UTF-8 и представления JSONB PostgreSQL 16.

SHA-256 отвечает за отпечаток содержимого; Ed25519 подтверждает подпись
доверенным ключом. Независимый pin (закреплённый SHA-256) защищает от подмены
точки доверия старой, даже корректно подписанной версией.

Первый снимок фиксирует исходное состояние, но не доказывает подлинность истории
до его создания. Checkpoint подтверждает только уже закреплённое доказательство.

### 10.2. WORM-архив (7.5B.4.2.2)

`audit-checkpoint-archive.py` создаёт и проверяет подписанные архивные конверты,
публикует их в выделенном AWS S3 с Object Lock в режиме COMPLIANCE.

WORM — Write Once, Read Many: записанные версии объекта нельзя произвольно
перезаписать или удалить до окончания срока блокировки.

Публикация требует проверки владельца bucket, versioning, Object Lock, retention,
байтов, точной версии объекта, подписи и отсутствия неожиданных версий/маркеров.
Используется условная запись `If-None-Match: *`. Ключи и AWS credentials отсутствуют
в backend и PostgreSQL. Хеши и UUID остаются чувствительными метаданными.

Доверенный реестр pin должен находиться вне PostgreSQL и независимого bucket,
принимать следующий переход атомарно (CAS) и предотвращать откат и развилки.
Утилита проверяет связь и следующий слот, но не разворачивает реестр сама.

### 10.3. Ключи и ротация

| Ключ | Назначение |
| --- | --- |
| Корневой архивный | Подписывает исходный архивный конверт, закреплён fingerprint |
| Текущий архивный | Подписывает очередные checkpoint; ротация подтверждается старым ключом |
| Независимый retention | Подписывает точное разрешение удаления |
| Status-signing | Подписывает отчёт Verifier для backend |

Приватные ключи хранятся раздельно, вне приложения. Архивная ротация сохраняет
проверяемость ранее подписанных конвертов. Утечка старого ключа не устраняется
обычной ротацией: требуется остановка подписания, расследование и новый
согласованный trust anchor при необходимости. Ротация status-signing выполняется
отдельно, с согласованным переключением закреплённого публичного ключа backend.

### 10.4. Защищённое удаление и ограничения

Реализован протокол подписанного разрешения retention с точным набором UUID,
отпечатком политики, сроком разрешения и внешней WORM-версией.
Проверяются только допустимые удаления, отсутствие подмены сохранившихся записей
и повторного появления уже удалённых идентификаторов.

Важно: протокол **ещё не интегрирован в SQL-очистку приложения**.
Утилита не выполняет DELETE и не оценивает правомерность удаления.
До production необходимо связать подписанное разрешение с транзакционным retention.

Ограничения текущих утилит: манифест до 128 MiB, цепочка до 2000 переходов,
до 50 000 удалений на разрешение и 1 млн удалённых ID в истории.
Истечение WORM-блокировки предшественника или достижение лимита требует
предварительно согласованной процедуры продолжения, а не сброса genesis.

Архив содержит доказательства, не полные данные журнала; он не заменяет backup.
До первого закрепления события могут быть скрыты/подменены источником.
Компрометация одновременно Verifier, signer и независимого pin выходит за пределы
гарантий этой схемы. Требуются независимые роли, инфраструктурный мониторинг и копии.

## 11. Независимый статус проверки

Этап 7.5B.4.3 реализует `audit-integrity-report.py` на отдельном verifier-хосте.
Процесс проверяет цепочку WORM, подписи, ротацию, retention, доверенный pin,
состояние следующего слота и текущий снимок PostgreSQL. Публикуется только статус.

### 11.1. Контракт статуса

`GET /api/admin/audit-events/integrity` возвращает `AuditIntegrityStatus`.
Ответ предназначен исключительно для `SUPER_ADMIN`, с `Cache-Control: no-store`.

| Поле | Значение |
| --- | --- |
| `state` | Состояние проверки |
| `checkedEvents` | Размер закреплённого внешнего снимка, а не текущего фильтра UI |
| `violations` | Число выявленных несоответствий |
| `unanchoredEvents` | Новые события, ещё не закреплённые снаружи |
| `checkedAt` | Время проверки |
| `freshUntil` | Конец срока действительности отчёта |
| `archiveStatus` | `AVAILABLE` или `UNKNOWN` |

Неизвестные значения — `null` в DTO, а не искусственные нули. Jackson с настройкой
`default-property-inclusion: non_null` может не включать эти поля в JSON. Состояния `VERIFIED`,
`PENDING`, `VIOLATION` содержат проверенные счётчики; неизвестное состояние
не подтверждает доступность архива. `checkedAt` относится к отчёту, не к нажатию кнопки.

### 11.2. Состояния

| Код | Состояние | Смысл |
| --- | --- | --- |
| 0 | `NOT_CONFIGURED` | Все три настройки отсутствуют |
| 1 | `VERIFIED` | Снимок совпадает, зелёный статус подтверждён |
| 2 | `VIOLATION` | Обнаружена подмена, исчезновение или возврат удалённого события |
| 3 | `UNAVAILABLE` | Отчёт или независимая проверка недоступны |
| 4 | `STALE` | Срок действия отчёта истёк |
| 5 | `INVALID` | Конфигурация, подпись, формат или поля не прошли проверку |
| 6 | `PENDING` | Есть ещё не закреплённые события, нарушений не обнаружено |

`PENDING` сам по себе не означает криптографическую подмену. Он блокирует зелёный статус.
Незавершённое разрешение retention или неожиданный следующий слот приводят
к `UNAVAILABLE`: Verifier не подтверждает актуальность цепочки в таком состоянии.
Ошибка и отсутствие данных никогда не трактуются как `VERIFIED`.

### 11.3. Граница backend

`AuditIntegrityReport` читает ограниченный ASCII-отчёт формата `safeai-audit-status-v1`:
dataset, Unix timestamp, состояние, три счётчика, статус архива и Base64-подпись.

- До 4096 байт, только обычный файл, без следования конечной символической ссылке.
- Канонический UUID dataset, публичный Ed25519 SPKI DER и подпись 64 байта.
- Проверка подписи над исходными байтами до доверия содержимому.
- Запрет будущего времени, некорректных счётчиков и противоречивых полей.
- Счётчики ограничены 10 млн; TTL — 900 секунд (15 минут), на границе отчёт устарел.
- Число нарушений не должно превышать сумму закреплённых и незакреплённых событий.
- I/O-сбой даёт `UNAVAILABLE`, ошибка криптографии или структуры — `INVALID`.
- Свежий подписанный `UNAVAILABLE` не содержит подтверждённых счётчиков.
- Отчёт перечитывается при запросе API и получении метрики; устаревший кеш не выдаётся.

Backend не выполняет запросы S3 и не создаёт новые checkpoint при чтении статуса.
Он доверяет только ограниченному отчёту с закреплённым публичным ключом.
Повтор ещё действительного отчёта возможен в пределах TTL; это не real-time ledger.

Пример ответа локального окружения без настроенного Verifier:

```json
{
  "state": "NOT_CONFIGURED",
  "archiveStatus": "UNKNOWN"
}
```

Это не ошибка API и не свидетельство успешной криптографической проверки.
HTTP 200 сообщает только о получении корректного статуса.

### 11.4. Настройка независимого контура

Подробные команды приведены в профильных README инфраструктуры (ссылки в конце).
На staging/production необходимо:

1. Создать отдельную PostgreSQL-роль `safeai_audit_verifier` с CONNECT только к нужной БД,
   USAGE на `public`, SELECT только на `audit_events`, без DDL/DML и лишних членств.
2. Настроить TLS `verify-full`, защищённые credentials, отдельный read-only IAM и S3 COMPLIANCE.
3. Независимо закрепить dataset, ключи, genesis и текущий pin.
4. Настроить запуск Verifier примерно каждые 5 минут без параллельного выполнения,
   с ограничением времени, подтверждённым SLA и синхронизацией NTP.
   Коды утилиты: 0 — VERIFIED, 1 — UNAVAILABLE или ошибка публикации,
   2 — VIOLATION, 3 — PENDING. Доставлять новый подписанный отчёт и при ненулевом коде.
5. Доставлять подписанный файл атомарной заменой в защищённый каталог.
   Backend имеет только доступ на чтение. В контейнер монтируется каталог, не отдельный inode.
6. Передать backend три публичные настройки и проверить доступность статуса на всех репликах.

```dotenv
SAFEAI_AUDIT_INTEGRITY_REPORT_PATH=/run/audit-integrity/status.txt
SAFEAI_AUDIT_INTEGRITY_DATASET=UUID_ИЗ_ДОВЕРЕННОЙ_КОНФИГУРАЦИИ
SAFEAI_AUDIT_INTEGRITY_PUBLIC_KEY=BASE64_DER_ED25519
```

Не помещать приватный ключ в переменную backend, Git, Docker-образ или `.env`.
Без настроек локальный интерфейс показывает «Независимая проверка не настроена».
Это корректное состояние разработки, но блокирующее условие для production.

запрос отменяется при размонтировании, истёкший отчёт перестаёт быть зелёным.

В развёрнутом виде отображаются закреплённые события, нарушения, незакреплённые

счётчики заменяются прочерками, архив не считается подтверждённым.
Подпись `WORM COMPLIANCE` означает подтверждение по отчёту, а не постоянный live-доступ.

## 13. Retention

`AuditRetentionService` запускает пакетную очистку по cron, по умолчанию в 03:30 UTC.
`AuditRetentionLockService` использует session-level PostgreSQL advisory lock,
исключающий одновременный запуск очистки разными репликами.

`AuditRetentionBatchService` удаляет партии в отдельных `REQUIRES_NEW`-транзакциях.
Cutoff рассчитывается через `clock_timestamp()` PostgreSQL. Событие не удаляется,
если в Outbox существует строка с тем же ID: конфликтующее доказательство сохраняется.

По умолчанию срок — 1095 суток, партия — 10 000, максимум 10 партий за запуск.
Таким образом, штатный предел составляет 100 000 записей за запуск.
Advisory lock занимает своё соединение; для пакетных транзакций нужны дополнительные
соединения пула. При ошибке release необходимо исключить unsafe connection из пула.

Поскольку протокол WORM retention пока не связан с SQL-очисткой, штатное удаление
закреплённой строки без корректного внешнего разрешения обнаружится как нарушение.
До производственной эксплуатации согласовать политику, legal hold, разрешения и
транзакционную интеграцию. Не обходить проблему отключением проверок или новым genesis.

## 16. Реагирование на инциденты

### Dead-letter или конфликт Outbox

1. Проверить backlog, возраст старейшей строки, heartbeat, ошибки доставки.
2. Проверить исходный ID и наличие соответствующего immutable evidence.
3. При конфликте сохранить обе записи, эскалировать ответственному за безопасность.
4. После устранения причины выполнить разрешённое восстановление через API.
5. Проверить исходный ID в истории, событие восстановления и прогресс очереди.

### Нарушение криптографической целостности (`VIOLATION`)

1. Объявить инцидент; сохранить отчёт, pin, версии объектов, манифесты и логи Verifier.
2. Операционно приостановить публикацию checkpoint и retention до расследования.
   Автоматическая блокировка SQL-очистки по отчёту пока не реализована.
3. Сверить независимые копии и восстановить обстоятельства изменения/удаления.
4. Не перезаписывать доказательства, не менять pin ради зелёного статуса.
5. Возобновлять операции по решению ответственного за безопасность.

### Нет доверенного отчёта (`INVALID`, `STALE`, `UNAVAILABLE`, `NOT_CONFIGURED`)

Проверить конфигурацию dataset/key/path, права файлов, доставку, подпись,
время, доступность PostgreSQL, TLS, IAM, S3 и внешний реестр pin.
Проверить отдельно работоспособность самого Verifier и Prometheus.
Не выдавать отсутствующий или просроченный отчёт за подтверждённую целостность.

### Производительность и известные ограничения

Открытые интервалы и исторические справочники (`DISTINCT ON`, поиск подстроки)
могут требовать сканирования большой истории. Проверять планы запросов на
репрезентативных объёмах, прежде чем добавлять индексы. Не считать ограничение
размера ответа ограничением стоимости SQL. При необходимости применять timeout,
rate limit и согласованный range policy без обхода tenant isolation.

Курсор v1 не имеет HMAC и привязки к фильтрам. Возможное усиление — новый формат
с отпечатком фильтров, TTL и проверкой подписи, с сохранением совместимости.
Это не подтверждённый обход авторизации: каждая выдача заново ограничивается scope.

Возраст backlog в метриках рассчитывается по JVM Clock, retry и retention — по
PostgreSQL. Требуется NTP. Не использовать age gauge как основание для удаления.
Нагрузочный прогон должен включать совместную работу retention, workers и API.

Приоритет после инфраструктуры: отдельная метрика ошибок выполнения и полный
асинхронный экспорт с лимитами, авторизацией, сроком хранения и собственным аудитом.
Они не являются уже реализованными возможностями.

**Текущий вердикт:** реализация этапа 7.5B.4.3 готова к дальнейшей стендовой приёмке;
production остаётся NO-GO до выполнения эксплуатационных условий.

## 19. Архитектурные инварианты

- Не нарушать атомарность обязательного аудита с бизнес-операцией.
- Не ослаблять required, RBAC, tenant isolation, Runtime ACL или миграционные проверки.
- Не переносить INSERT истории и DELETE Outbox в разные транзакции.
- Не удалять `SKIP LOCKED`, блокировки recovery и проверки равенства evidence.
- Не изменять immutable snapshots, `correlation_id` и терминальные записи Outbox.
- Не подменять исторического инициатора текущими данными пользователя.
- Не использовать Correlation ID, курсор или UUID как средство авторизации.
- Не расширять allowlist без анализа приватности; не логировать секреты и raw details.
- Не изменять применённые Flyway-миграции V1–V94; новые изменения — новой миграцией.
- Не смешивать ключ подписи архива, retention и статусный ключ; не передавать их backend.
- Не считать наличие файла, S3-объекта или HTTP 200 доказательством целостности.
- Не сообщать зелёный статус без свежей доверенной подписи и согласованных данных.
- Не перезаписывать checkpoint, не откатывать pin и не сбрасывать genesis при инциденте.
- Не удалять закреплённое evidence без одобренного протокола retention.
- Не ослаблять тесты, coverage и правила проверки ради зелёного CI.
